# Plain Language｜把复杂东西讲成人话

## 1. 目标

技术文章不是把术语翻译成更长的术语。

目标是让读者先知道：

- 这个东西在干什么；
- 它具体改变了哪一步；
- 为什么值得关心；

然后再告诉他官方名字、机制和边界。

> **先讲动作和结果，再讲名词。**

## 2. 产品名不等于解释

不要写：

> Space、Pages、Meetings、Team Tasks 共同构成新的协作工作流。

这句话每个词都认识，但普通读者不知道画面是什么。

优先写：

> 开会之后，会议记录可以直接进项目空间；同事在页面里改文档、留评论，Agent 再接着处理。

等读者已经有画面，再补：

> 这些能力分别落在 Space、Pages 和 Meetings 里。

### 判断标准

把产品名、模型名、缩写遮住以后，这段话还剩不剩一个普通人能复述的动作？

如果只剩抽象名词，重写。

## 3. 一个句子只承担一个主要新概念

警惕这种句子：

> MCP Events、Team Tasks、Plugin Extensions 和 Sign in with ChatGPT 让 Agent 在更多第三方工作流里持续协作。

它一次塞进四个陌生词，还要求读者理解“第三方工作流”“持续协作”。

更自然的拆法：

> 外部软件有新消息时，可以通知 ChatGPT 继续处理任务。这个能力叫 MCP Events。
>
> 团队还可以把这类任务保存下来，定时跑或者由事件触发，这部分叫 Team Tasks。

不是禁止长句，而是不要让一句话同时承担太多第一次出现的新东西。

### 术语拥挤报警

以下不是硬指标，但出现时要检查：

- 一句话里出现 3 个以上陌生产品名 / 缩写；
- 一段里连续出现 4 个以上新名词，却没有动作、例子或结果；
- 一句话能画出“名词关系图”，却画不出“人在做什么”。

## 4. 首次出现：先给人话锚点

陌生概念第一次出现时，优先采用：

> **一句人话 → 官方名词 → 必要边界**

例如：

> 第三方软件里出现一条新消息，可以直接把 ChatGPT 叫起来继续干活。OpenAI 把这套事件通知能力叫 MCP Events。
>
> 它不是让 ChatGPT 自动偷看所有消息，前提是插件支持事件，用户也配置了要关注什么。

而不是：

> MCP Events 是基于 MCP 的事件驱动扩展机制……

## 5. 抽象名词尽量还原成动作

看到这些词时要特别警惕：

- 工作流；
- 协作；
- 生态；
- 能力；
- 场景；
- 接入；
- 触发；
- 编排；
- 持续执行；
- 上下文；
- 统一入口；
- 集中管理。

它们不是不能用，但最好先问：

> **谁，在什么地方，做了什么？**

例如：

“支持多人协作”

可以改成：

> 你在页面里改一段，同事可以直接评论；需要 AI 接手时，@ 它继续改。

“接入外部数据源”

可以改成：

> 把 Slack 里的反馈、Google Drive 的文件或者 GitHub 里的代码拉进来一起处理。

## 6. 具体演示优先于概念解释

有现场 demo 时，先写动作：

> Holly 在页面里按下 /，插入一张可以筛选的数据图，又 @ 两位同事一起看。

再解释：

> 这就是 Space 想解决的事：聊天产生的东西，不用再复制到另一个地方，后续编辑和协作都留在同一个项目里。

如果先写“Space 是集中式协作工作空间”，读者很容易失去画面。

## 7. 配套信息优先顺手串讲

边角更新可以信息很多，但普通分享不必为每个名字制造一个知识点。相关信息先挂回当前话题，讲需要它解决的事；把句子译成人话以后，再检查是否仍像补一份产品目录。

坏例子：

> MCP Events、Team Tasks、Plugin Extensions、Marketplace、Private Intelligence 等进一步完善了企业生态。

可以这样串进去：

讲持续处理任务时，顺带说新消息可以主动通知 ChatGPT，这叫 MCP Events；团队还能把同一类工作保存成长期任务，按时间或指定事件运行。

讲团队一起改文档时，补一句 Slack、Teams 这些聊天软件里也能 @ChatGPT，让它根据正在讨论的事帮忙。

讲编程工具时，把漏洞检查放在代码改完之后；讲插件时，再说它能在 ChatGPT 里打开界面，以及符合条件的外部应用可以使用已有订阅额度。

剩下的企业采购、数据隐私能力，可以用短段收住，不必展开一串子产品名。用户明确要完整发布清单或便于查找的对照时再单列，每条仍要独立可懂。必要限制按真实来源保留。

## 8. 复述测试

每写完一个重要小节，静默问：

> 如果读者把这一段转述给朋友，他会怎么说？

如果答案只能是：

> “OpenAI 推出了 Space、Pages、Meetings、Plugin Extensions……”

说明读者记住的只是名词。

更理想的是：

> “OpenAI 想把聊天里做出来的东西留在一个项目空间里，同事能一起改，会议记录也能直接接进来。”

名词可以忘，事情要先懂。

## 9. 不要为了通俗而失真

“讲人话”不是删除技术边界。

顺序应该是：

> 先给直觉 → 再给具体动作 → 再补准确机制 / 限制

技术名词、价格条件、开放范围、权限边界仍然保留，只是不要让它们挡在理解前面。

## 10. 最终检查

- [ ] 每个陌生产品第一次出现时，读者先知道它在干什么；
- [ ] 一句话没有塞进过多第一次出现的名词；
- [ ] 抽象词旁边有动作或结果；
- [ ] 有真实 demo 时，先写人做了什么、页面发生了什么；
- [ ] 配套信息优先挂回相关话题，没有默认制造杂项清单；确实需要清单时每条独立可懂；
- [ ] 遮住所有产品名后，正文仍然有清楚的画面；
- [ ] 普通读者不需要先理解“工作流 / 生态 / 编排”等词才能继续读；
- [ ] 通俗化没有牺牲事实边界。
