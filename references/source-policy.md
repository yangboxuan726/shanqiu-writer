# Source Policy｜事实与来源边界

## 四类来源必须分清

1. 官方说法；
2. 独立第三方测评；
3. X / 社区公开案例；
4. 山丘亲测。

不要把它们混成同一场 benchmark。

“分清来源”不等于“每个截图、每段代码、每句原话都重复标一个出处”。

来源可以通过正文、链接、图注、上下文中的明确指代来建立。只要普通读者能判断“这是谁说的 / 谁测的 / 这段材料从哪来”，就已经达到目的。

不要为了形式统一，把文章写成论文式注释。

## 官方材料

适合证明：
- 发布时间；
- 官方定位；
- API 价格；
- 官方 benchmark；
- 产品功能声明。

官方 benchmark 不能自动等同于作者实际体验。

## 第三方案例

适合提供：
- 别人的实际展示；
- 更多任务类型；
- 额外视角。

写清是谁做的、条件是什么。没有统一条件时，不下“谁赢了”的结论。

## 作者亲测

只有实际做过的事才能写“我测了”。

保留真实过程，包括失败、卡住、重试、没搞懂。

## 静态图边界

静态截图可以评价：
- 构图；
- 场景元素；
- 视觉细节。

不能仅凭静态图判断：
- 动画是否自然；
- 快捷键是否生效；
- Agent 是否完整验证；
- 交互是否无 bug。

## 不确定时

直接写：
- “这点我现在不能确定。”
- “公开信息只能证明到这里。”

不要为了文章完整度补猜测。


## 来源标注的最小充分原则

优先做到“最小充分”：

- 正文已经说“官方文档里写着”，紧接官方截图：通常无需再写“图：官方截图”；
- 正文已经说明“下面是我自己跑的结果”，紧接作者截图：无需重复标“作者亲测”；
- 一段代码前已经写明“这是 Pi 官方示例”，代码块后无需再次注明；
- 官方材料和第三方材料连续出现时，要在切换处明确告诉读者来源变了；
- 第三方案例、社区截图、他人测试，若上下文无法自然说明，优先在图注或正文里标清作者 / 来源；
- 承担关键结论的证据，来源身份不能含糊。

判断标准不是“有没有写来源格式”，而是：

> **读者会不会误以为这是作者亲测、官方结论，或者同一条件下的对比结果？**

如果不会，就不必重复标。
