# Evals｜回归测试

每次改 Skill 后，至少用下面场景检查一次。

## Case 1｜热点模型发布

输入：三个新模型同日发布，含官方价格、benchmark、作者对其中两个做了同题实测，第三个只有公开案例。

检查：
- [ ] 前 150 字内进入核心问题；
- [ ] 不先翻译完整发布会；
- [ ] 亲测与第三方案例明确分开；
- [ ] 最有说服力的图 / 数字出现得足够早；
- [ ] 没有硬排三方胜负；
- [ ] 文章不是参数汇总。

## Case 2｜技术解释

输入：解释 BM25 / OAuth / MCP。

检查：
- [ ] 先有一个真实问题；
- [ ] 先直觉、例子，再机制和术语；
- [ ] 非技术读者能继续看；
- [ ] 技术读者不会觉得胡扯；
- [ ] 没有为了全面写百科。

## Case 3｜产品实测

输入：一个 AI 客户端连续卡住 40 分钟，但最终完成。

检查：
- [ ] 先给过程证据；
- [ ] 允许明确写不满意；
- [ ] 不把卡顿原因猜成确定事实；
- [ ] 吐槽来自真实过程；
- [ ] 不把体验稿写成功能列表。

## Case 4｜去 AI 味

输入：一篇结构完整、事实正确、但像行业报告的初稿。

检查：
- [ ] 是否敢删 30% 以上废话；
- [ ] 是否打破工整段落；
- [ ] 是否删除机械过渡和重复总结；
- [ ] 是否保留作者真实判断；
- [ ] 是否避免凭空制造个人经历。

## Case 5｜长度

检查：
- [ ] 没有固定字数目标；
- [ ] 短文不会被强行拉长；
- [ ] 长文每一屏仍然有新东西。

## Case 6｜标题与转场

输入：一篇同时包含作者亲测、价格差异、第三方案例、官方 Benchmark 的热点文章。

检查：
- [ ] 主标题不是全文摘要；
- [ ] 标题爆点来自正文真实事实；
- [ ] 尝试了多个标题方向，而不是顺手总结一句；
- [ ] 封面标题可以比主标题更短；
- [ ] 正文小标题没有全部写成 PPT 目录；
- [ ] 切到新模型 / 新材料前，解释了“为什么现在要讲它”；
- [ ] 从作者亲测切到第三方案例时，叙述视角明确切换；
- [ ] 复杂图表先告诉普通读者“看哪里”；
- [ ] 中段没有连续很久只有数据、没有作者反应。

## Case 7｜IP 世界观与开头

输入：一篇 AI 热点或产品文章，作者品牌名仍可能调整，长期内容方向也不局限于代码。

检查：
- [ ] 开头没有无意义的“大家好，我是……”；
- [ ] 第一屏直接进入事件、冲突、画面、情绪或结果；
- [ ] 没有把“程序员 / 学生 / 产品经理”写成整个 IP 的固定身份；
- [ ] 内容可以自然容纳模型、产品、技术、创业和个人思考；
- [ ] 没有为了体现世界观，强行把普通文章升华到 AGI / 文明；
- [ ] 如果没有亲测，也没有伪装成亲测，公开案例和官方材料来源清楚；
- [ ] 文章即使混合热点、实测和科普，读者仍然只感觉有一条主线。


## Case 8｜学习 / 认知转变型

输入：作者昨晚研究 Pi Agent 与 DeepSeek Harness。已有官方资料和一版技术上正确的初稿，但初稿更像技术评论；真实学习过程中，作者原本把 Agent 理解成“模型 + 工具 + Loop”，后来因为 Pi 的极简设计与 DeepSeek 的插件化设计，开始把注意力转向“一个 Harness 到底替用户做多少决定”。

检查：
- [ ] 没有把文章退化成 Pi / DeepSeek 功能对照表；
- [ ] 保留真实的起始理解、关键反差和现在的理解；
- [ ] 认知变化不是虚构的“顿悟故事”；
- [ ] 个人视角没有压过技术事实，关键结论仍有资料支撑；
- [ ] 没有把学习过程写成“昨晚先看 A，再看 B，再看 C”的流水账；
- [ ] 技术解释在读者产生问题时出现，而不是先把定义讲完；
- [ ] 最后抽象出的设计哲学来自前文事实，而不是硬升华；
- [ ] 即使删掉“我”的部分，事实仍然成立；加回“我”之后，读者更容易理解为什么这些事实值得放在一起看。


## Case 9｜作者稿 vs Skill 稿校准

输入：同一主题有两版文章。一版由 Skill 生成，结构清楚、信息密度高、总结很漂亮；另一版是作者自己写的，排版较乱，但保留了更多代码、截图、具体探索过程和局部停顿。作者明确更喜欢第二版的内容气质。

检查：
- [ ] 不把“更短、更整齐”默认当成更好；
- [ ] 不因为作者稿存在毛边，就把它重新修回 Skill 稿的对称结构；
- [ ] 找出作者稿里反复出现的稳定偏好，而不是逐句模仿；
- [ ] 技术结论前保留足够的一手证据，让读者知道判断从哪来；
- [ ] 允许“先看实现，再长出观点”，而不是强制观点先行；
- [ ] 允许局部深入一个实现细节，即使它不是最短路径；
- [ ] 小标题可以只是定位，不要求每个都像金句；
- [ ] 最终成稿应比作者原稿更清楚，但不能比作者原稿更像“编辑部文章”；
- [ ] 如果删掉一段会让文章更利落，却同时删掉“作者为什么会得出这个判断”的依据，则优先保留或压缩而不是删除。


## Case 10｜高可读性长文校准

输入：一篇素材很扎实的 AI 技术 / 产品长文。当前版本使用了明显品牌色、小标题、重点卡片，逻辑正确但有“模板感”。参考优秀长文后，希望提高“让人一直读下去”的能力，但不能模仿具体作者的口癖和人格。

检查：
- [ ] 去掉品牌色后，文章层级仍然成立；
- [ ] 小标题数量来自定位需要，而不是模板要求；
- [ ] 文章有一根可追踪的主线，旁支结束后能自然回扣；
- [ ] 知识点是在读者产生问题时出现，而不是集中科普；
- [ ] 多案例 / 多模型有发现顺序，没有一次性把惊喜总结完；
- [ ] 至少有几处“事实 / 图 / 代码 → 作者反应 → 新问题”的推进；
- [ ] 没有复制参考作者的固定口头禅、标点癖好、脏话或人格设定；
- [ ] AI 没有替作者虚构第一手经历、情绪和核心观点；
- [ ] 结尾优先考虑自然回环或具体判断，而不是机械总结；
- [ ] 全文即使保持中性黑白排版，也仍然有阅读吸引力。


## Case 11｜作者资产保真

输入：作者给出一版自己写的技术文章，其中有局部啰嗦、真实代码、一些不够漂亮的转场，以及几个明显属于作者自己的困惑和判断。要求 Skill 优化。

检查：
- [ ] 优化前先识别哪些内容属于“作者资产”；
- [ ] 不为了篇幅漂亮删除关键代码、截图或认知转折；
- [ ] 没有把作者真实但略粗糙的表达全部换成标准公众号句式；
- [ ] “我”的存在来自具体观察和判断，而不是额外添加口语词；
- [ ] AI 没有替作者发明更高级的核心观点；
- [ ] 每次补知识都是为了解答正文已经出现的问题；
- [ ] 修改后比原稿更容易读，但仍能看出作者本人为什么会写这篇；
- [ ] 如果作者版本与 Skill 版本冲突，优先分析稳定偏好，而不是默认 Skill 正确。


## Case 12｜对象驱动封面

输入：一篇《Pi Agent 与 DeepSeek Harness 的设计哲学》文章。作者希望封面唯美、有编辑感、AI 味低。DeepSeek 有明确鲸鱼品牌视觉，Pi 可以从 Pi / π、极简、少工具、专注感中提炼视觉。之前错误方案曾无理由使用星球、太阳和泛科技场景。

检查：
- [ ] 封面先从 Pi 与 DeepSeek 本身寻找视觉锚点，而不是先套“AI 科技风”；
- [ ] DeepSeek 的视觉语言可被识别，且不随意创造与品牌无关的 mascot；
- [ ] Pi 一侧能表达极简 / 专注 / 少工具，而不是只写一个产品名；
- [ ] “极简 vs 模块化”的核心差异在画面里可感知；
- [ ] 唯美元素与主题对象或文章含义有关，不无理由加入星球、太阳、宇宙等意象；
- [ ] 画面克制、有编辑感，而不是廉价赛博海报；
- [ ] 不依赖固定绿色、固定左文右图或固定标签模板；
- [ ] 中文文字足够少，完整文章标题没有被硬塞进封面；
- [ ] 缩小成公众号列表封面后，主体和关系仍然可辨；
- [ ] 把标题替换成另一篇 AI 文章后，这张图不能轻易继续使用。
