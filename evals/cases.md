# Evals｜回归测试

每次改 Skill 后，至少用下面场景检查一次。

## Case 1｜热点模型发布

输入：三个新模型同日发布，含官方价格、benchmark、作者对其中两个做了同题实测，第三个只有公开案例。

检查：
- [ ] 前 150 字内进入核心问题；
- [ ] 不先翻译完整发布会；
- [ ] 亲测与第三方案例明确分开；
- [ ] 最有说服力的图 / 数字出现得足够早；
- [ ] 没有硬排三方胜负；
- [ ] 文章不是参数汇总。

## Case 2｜技术解释

输入：解释 BM25 / OAuth / MCP。

检查：
- [ ] 先有一个真实问题；
- [ ] 先直觉、例子，再机制和术语；
- [ ] 非技术读者能继续看；
- [ ] 技术读者不会觉得胡扯；
- [ ] 没有为了全面写百科。

## Case 3｜产品实测

输入：一个 AI 客户端连续卡住 40 分钟，但最终完成。

检查：
- [ ] 先给过程证据；
- [ ] 允许明确写不满意；
- [ ] 不把卡顿原因猜成确定事实；
- [ ] 吐槽来自真实过程；
- [ ] 不把体验稿写成功能列表。

## Case 4｜去 AI 味

输入：一篇结构完整、事实正确、但像行业报告的初稿。

检查：
- [ ] 是否敢删 30% 以上废话；
- [ ] 是否打破工整段落；
- [ ] 是否删除机械过渡和重复总结；
- [ ] 是否保留作者真实判断；
- [ ] 是否避免凭空制造个人经历。

## Case 5｜长度

检查：
- [ ] 没有固定字数目标；
- [ ] 短文不会被强行拉长；
- [ ] 长文每一屏仍然有新东西。

## Case 6｜标题与转场

输入：一篇同时包含作者亲测、价格差异、第三方案例、官方 Benchmark 的热点文章。

检查：
- [ ] 主标题不是全文摘要；
- [ ] 标题爆点来自正文真实事实；
- [ ] 尝试了多个标题方向，而不是顺手总结一句；
- [ ] 封面标题可以比主标题更短；
- [ ] 正文小标题没有全部写成 PPT 目录；
- [ ] 切到新模型 / 新材料前，解释了“为什么现在要讲它”；
- [ ] 从作者亲测切到第三方案例时，叙述视角明确切换；
- [ ] 复杂图表先告诉普通读者“看哪里”；
- [ ] 中段没有连续很久只有数据、没有作者反应。

## Case 7｜IP 世界观与开头

输入：一篇 AI 热点或产品文章，作者品牌名仍可能调整，长期内容方向也不局限于代码。

检查：
- [ ] 开头没有无意义的“大家好，我是……”；
- [ ] 第一屏直接进入事件、冲突、画面、情绪或结果；
- [ ] 没有把“程序员 / 学生 / 产品经理”写成整个 IP 的固定身份；
- [ ] 内容可以自然容纳模型、产品、技术、创业和个人思考；
- [ ] 没有为了体现世界观，强行把普通文章升华到 AGI / 文明；
- [ ] 如果没有亲测，也没有伪装成亲测，公开案例和官方材料来源清楚；
- [ ] 文章即使混合热点、实测和科普，读者仍然只感觉有一条主线。


## Case 8｜学习 / 认知转变型

输入：作者昨晚研究 Pi Agent 与 DeepSeek Harness。已有官方资料和一版技术上正确的初稿，但初稿更像技术评论；真实学习过程中，作者原本把 Agent 理解成“模型 + 工具 + Loop”，后来因为 Pi 的极简设计与 DeepSeek 的插件化设计，开始把注意力转向“一个 Harness 到底替用户做多少决定”。

检查：
- [ ] 没有把文章退化成 Pi / DeepSeek 功能对照表；
- [ ] 保留真实的起始理解、关键反差和现在的理解；
- [ ] 认知变化不是虚构的“顿悟故事”；
- [ ] 个人视角没有压过技术事实，关键结论仍有资料支撑；
- [ ] 没有把学习过程写成“昨晚先看 A，再看 B，再看 C”的流水账；
- [ ] 技术解释在读者产生问题时出现，而不是先把定义讲完；
- [ ] 最后抽象出的设计哲学来自前文事实，而不是硬升华；
- [ ] 即使删掉“我”的部分，事实仍然成立；加回“我”之后，读者更容易理解为什么这些事实值得放在一起看。


## Case 9｜作者稿 vs Skill 稿校准

输入：同一主题有两版文章。一版由 Skill 生成，结构清楚、信息密度高、总结很漂亮；另一版是作者自己写的，排版较乱，但保留了更多代码、截图、具体探索过程和局部停顿。作者明确更喜欢第二版的内容气质。

检查：
- [ ] 不把“更短、更整齐”默认当成更好；
- [ ] 不因为作者稿存在毛边，就把它重新修回 Skill 稿的对称结构；
- [ ] 找出作者稿里反复出现的稳定偏好，而不是逐句模仿；
- [ ] 技术结论前保留足够的一手证据，让读者知道判断从哪来；
- [ ] 允许“先看实现，再长出观点”，而不是强制观点先行；
- [ ] 允许局部深入一个实现细节，即使它不是最短路径；
- [ ] 小标题可以只是定位，不要求每个都像金句；
- [ ] 最终成稿应比作者原稿更清楚，但不能比作者原稿更像“编辑部文章”；
- [ ] 如果删掉一段会让文章更利落，却同时删掉“作者为什么会得出这个判断”的依据，则优先保留或压缩而不是删除。


## Case 10｜高可读性长文校准

输入：一篇素材很扎实的 AI 技术 / 产品长文。当前版本使用了明显品牌色、小标题、重点卡片，逻辑正确但有“模板感”。参考优秀长文后，希望提高“让人一直读下去”的能力，但不能模仿具体作者的口癖和人格。

检查：
- [ ] 去掉品牌色后，文章层级仍然成立；
- [ ] 小标题数量来自定位需要，而不是模板要求；
- [ ] 文章有一根可追踪的主线，旁支结束后能自然回扣；
- [ ] 知识点是在读者产生问题时出现，而不是集中科普；
- [ ] 多案例 / 多模型有发现顺序，没有一次性把惊喜总结完；
- [ ] 至少有几处“事实 / 图 / 代码 → 作者反应 → 新问题”的推进；
- [ ] 没有复制参考作者的固定口头禅、标点癖好、脏话或人格设定；
- [ ] AI 没有替作者虚构第一手经历、情绪和核心观点；
- [ ] 结尾优先考虑自然回环或具体判断，而不是机械总结；
- [ ] 全文即使保持中性黑白排版，也仍然有阅读吸引力。


## Case 11｜作者资产保真

输入：作者给出一版自己写的技术文章，其中有局部啰嗦、真实代码、一些不够漂亮的转场，以及几个明显属于作者自己的困惑和判断。要求 Skill 优化。

检查：
- [ ] 优化前先识别哪些内容属于“作者资产”；
- [ ] 不为了篇幅漂亮删除关键代码、截图或认知转折；
- [ ] 没有把作者真实但略粗糙的表达全部换成标准公众号句式；
- [ ] “我”的存在来自具体观察和判断，而不是额外添加口语词；
- [ ] AI 没有替作者发明更高级的核心观点；
- [ ] 每次补知识都是为了解答正文已经出现的问题；
- [ ] 修改后比原稿更容易读，但仍能看出作者本人为什么会写这篇；
- [ ] 如果作者版本与 Skill 版本冲突，优先分析稳定偏好，而不是默认 Skill 正确。


## Case 12｜对象驱动封面

输入：一篇《Pi Agent 与 DeepSeek Harness 的设计哲学》文章。作者希望封面唯美、有编辑感、AI 味低。DeepSeek 有明确鲸鱼品牌视觉，Pi 可以从 Pi / π、极简、少工具、专注感中提炼视觉。之前错误方案曾无理由使用星球、太阳和泛科技场景。

检查：
- [ ] 封面先从 Pi 与 DeepSeek 本身寻找视觉锚点，而不是先套“AI 科技风”；
- [ ] DeepSeek 的视觉语言可被识别，且不随意创造与品牌无关的 mascot；
- [ ] Pi 一侧能表达极简 / 专注 / 少工具，而不是只写一个产品名；
- [ ] “极简 vs 模块化”的核心差异在画面里可感知；
- [ ] 唯美元素与主题对象或文章含义有关，不无理由加入星球、太阳、宇宙等意象；
- [ ] 画面克制、有编辑感，而不是廉价赛博海报；
- [ ] 不依赖固定绿色、固定左文右图或固定标签模板；
- [ ] 中文文字足够少，完整文章标题没有被硬塞进封面；
- [ ] 缩小成公众号列表封面后，主体和关系仍然可辨；
- [ ] 把标题替换成另一篇 AI 文章后，这张图不能轻易继续使用。

## Case 13｜大会分享与完整实录

输入：用户提供三篇同一场大会的参考文章，一篇侧重门槛和价格，一篇带有亲测与竞品判断，一篇按演讲顺序完整记录发布和演示。用户先要求「让普通读者看懂主要发布」，随后可能改为「逐项详解，保留现场过程」。作者没有提供通宵观看或亲测经历。

检查：
- [ ] 先按用户目的选择有重点的分享或完整实录，不把三篇参考揉成固定模板；
- [ ] 普通分享覆盖主要发布，对具体演示、前后变化或成本问题分配更多篇幅；
- [ ] 完整实录保留应有发布项和现场顺序，可以前置发布地图，不为单一观点强行删内容；
- [ ] 演示中的指令、结果和失败都有来源，不把官方展示写成作者亲测或普遍交付承诺；
- [ ] 没有移植参考作者的经历、情绪、竞品偏好或未经核实的传闻；
- [ ] 并列发布可以直接转场，没有为了段落连接编造疑问和悬念；
- [ ] 没有用固定比例、图片数量或评价频率代替阅读判断；
- [ ] 必要价格口径、开放条件和来源清楚，核查日志没有反复打断正文。
- [ ] 每节能指出一个主要停留点，并由具体材料推进，没有换了开头又补回完整能力清单；
- [ ] 连续定义、能力或条件说明过多时，重选组织单位，而非插入“我觉得”或装饰图；
- [ ] 删改比例只作参考，必要费用口径、来源、失败细节和明确要求保留的内容仍在。


## Case 14｜分享感 vs 说明书

输入：一篇 OpenAI DevDay 多项发布稿。当前版本开头先用三句总结大会，再放“你想解决什么问题 → 对应发布”的表格，并提前提出“一套完整工作方式”；后面每节都按产品定位、能力、条件、限制解释。参考样本则更多直接展示发布、现场截图、演示过程、价格变化和作者有依据的反应。

检查：
- [ ] 开头先让具体发布出现，而不是先替二十多项更新建立完整体系；
- [ ] 如果需要总览，优先发布地图 / 清单，而不是默认问题分类矩阵；
- [ ] 有官方演示、现场截图或真实上手时，不用通用假设场景替代；
- [ ] 至少几个重点项能让读者“看见它怎么发生”，而不只是知道“它负责什么”；
- [ ] 产品之间没有真实因果时允许直接转场，不硬造悬念；
- [ ] 小标题优先承担定位，允许直接写 Dots、ChatGPT Space、GPT-6.1 Sol、500 美元 Pro 等；
- [ ] 限制、开放条件和来源准确，但没有每个产品都平均铺成说明书模板；
- [ ] 整体判断在材料之后形成，不是一开头就宣布大会的唯一主线；
- [ ] 文章读起来像“有人替我看过，现在挑值得看的讲给我听”，而不是“有人替我整理了一份产品手册”。


## Case 15｜高覆盖但不平均

输入：一场发布会包含 20+ 项更新。用户喜欢的参考文章信息量很大，既包含主发布的详细演示，也保留价格、门槛、次要更新和现场细节。当前优化建议容易滑向“只保留几个重点”。

检查：
- [ ] 主要发布和关键价格 / 开放条件没有因为追求可读性被删掉；
- [ ] 次要更新仍然有覆盖，不默认全部压成一句“还有若干更新”；
- [ ] 主发布、次重点、配套更新的篇幅和解释深度明显不同；
- [ ] 有价值的小细节可以突破层级，多停一会，不被“它只是次要更新”机械压缩；
- [ ] 高信息量通过图片、表格、清单、短段落等不同介质承载，而不是全部堆成连续说明文字；
- [ ] 文章读完后，读者既知道主要发生了什么，也能记住少数重点和具体瞬间；
- [ ] 没有把“去说明书味”误写成“减少信息量”。


## Case 16｜名词都对，但人看不懂

输入：一篇发布会文章中连续出现多个产品名、缩写和抽象概念，事实基本正确，但普通读者读完不知道这些东西具体在干什么。

检查：
- [ ] 每个陌生产品第一次出现前后，有一句不依赖该产品名的人话解释；
- [ ] 优先描述台上实际动作、界面变化或用户结果，再给概念名；
- [ ] 一句话没有承担过多第一次出现的新名词；
- [ ] “工作流 / 协作 / 生态 / 接入 / 编排”没有替代具体动作；
- [ ] Space 能被普通读者复述成“同一个项目里放资料、改页面、让同事和 AI 接着做”，而不只是记住产品名；
- [ ] 配套信息优先挂回相关话题，只有用户需要完整清单或查找时才默认单列，每条仍独立可懂；
- [ ] 遮住所有产品名后，正文仍然能看出谁做了什么；
- [ ] 通俗化没有删除价格、权限、开放范围或其他必要事实边界。
- [ ] 陌生名称只在需要时出现，没有把杂项列表改成无项目符号的术语长句；
- [ ] 作者删改前文后，人物、指代和演示背景仍有来处，作者新增经历、图片和观点没有被旧稿覆盖。

## Case 17｜第一次读系列评测

输入：一篇接着上期写的三模型评测。作者提供同题 SVG、HTML 的一次生成结果，客户端和推理档位已确认，正文只放截图；旧开头直接说“又叫企鹅回来”。读者没有看过上期，也不知道 SVG 和 HTML 是什么。

检查：
- [ ] 不读上期也能说清为什么比较这些模型、这次让它们做什么；
- [ ] 结果出现前能辨认这是写代码做画面，规则来自真实记录，没有擅自补“无参考图”“算力相同”等条件；
- [ ] 开头上下文足够但不变成长背景或测试方法清单；
- [ ] 每轮图前有一个具体、可从图里检查的看点，不只说“再看下一题”；
- [ ] 标题提供本篇结果或体验撑得住的点击理由，没有把普通题夸成“狠题”或宣判全面胜负；
- [ ] 原题有动态要求，但没有用截图证明运动、交互或精确速度；
- [ ] 本篇需要的价格与使用条件独立交代，作者后补的真实体验和图片仍在。


## Case 17｜同一个生图模型，Prompt 被 Skill 束缚

输入：同一篇模型实测文章使用同一类 image generation 能力。一个版本把 Skill 中的“低 AI 味、编辑感、对象锚点、克制、不要赛博”等规则全部塞进提示词，结果生成米白纸张、扁平插画、双栏拼贴；另一个版本只给“模型 PK + 机场 / 企鹅主视觉 + 高完成度商业封面 + 强层级 + 标题”，结果明显更有视觉冲击力。

检查：
- [ ] 没有把 cover-design 的完整规则逐条抄进 image prompt；
- [ ] Skill 用于前置判断和后置验收，image prompt 只保留真正影响画面的少数约束；
- [ ] “低 AI 味”没有被误解成低对比、低饱和、扁平、纸张拼贴；
- [ ] 允许根据主题选择电影感、3D、半写实、商业广告级质感；
- [ ] 画面存在一个强主视觉，不是多个小元素平均分布；
- [ ] 小图第一眼有焦点和冲击力；
- [ ] 仍然能看出文章对象和核心关系，没有为了好看跑题；
- [ ] 不把某一次成功封面的具体风格固化成以后所有封面的默认模板。
