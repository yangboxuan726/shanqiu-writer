# Evals｜回归测试

每次改 Skill 后，至少用下面场景检查一次。

## Case 1｜热点模型发布

输入：三个新模型同日发布，含官方价格、benchmark、作者对其中两个做了同题实测，第三个只有公开案例。

检查：
- [ ] 前 150 字内进入核心问题；
- [ ] 不先翻译完整发布会；
- [ ] 亲测与第三方案例明确分开；
- [ ] 最有说服力的图 / 数字出现得足够早；
- [ ] 没有硬排三方胜负；
- [ ] 文章不是参数汇总。

## Case 2｜技术解释

输入：解释 BM25 / OAuth / MCP。

检查：
- [ ] 先有一个真实问题；
- [ ] 先直觉、例子，再机制和术语；
- [ ] 非技术读者能继续看；
- [ ] 技术读者不会觉得胡扯；
- [ ] 没有为了全面写百科。

## Case 3｜产品实测

输入：一个 AI 客户端连续卡住 40 分钟，但最终完成。

检查：
- [ ] 先给过程证据；
- [ ] 允许明确写不满意；
- [ ] 不把卡顿原因猜成确定事实；
- [ ] 吐槽来自真实过程；
- [ ] 不把体验稿写成功能列表。

## Case 4｜去 AI 味

输入：一篇结构完整、事实正确、但像行业报告的初稿。

检查：
- [ ] 是否敢删 30% 以上废话；
- [ ] 是否打破工整段落；
- [ ] 是否删除机械过渡和重复总结；
- [ ] 是否保留作者真实判断；
- [ ] 是否避免凭空制造个人经历。

## Case 5｜长度

检查：
- [ ] 没有固定字数目标；
- [ ] 短文不会被强行拉长；
- [ ] 长文每一屏仍然有新东西。

## Case 6｜标题与转场

输入：一篇同时包含作者亲测、价格差异、第三方案例、官方 Benchmark 的热点文章。

检查：
- [ ] 主标题不是全文摘要；
- [ ] 标题爆点来自正文真实事实；
- [ ] 尝试了多个标题方向，而不是顺手总结一句；
- [ ] 封面标题可以比主标题更短；
- [ ] 正文小标题没有全部写成 PPT 目录；
- [ ] 切到新模型 / 新材料前，解释了“为什么现在要讲它”；
- [ ] 从作者亲测切到第三方案例时，叙述视角明确切换；
- [ ] 复杂图表先告诉普通读者“看哪里”；
- [ ] 中段没有连续很久只有数据、没有作者反应。
